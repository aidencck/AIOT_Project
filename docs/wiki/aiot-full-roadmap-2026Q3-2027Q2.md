# AIOT 全项目路线图（2026Q3-2027Q2）

状态：`planned`

适用角色：`AIOT 产研负责人 / 架构负责人 / 产品负责人 / 交付负责人`

## 1. Premise（前提）

- 当前项目已经完成 AIoT 平台的基础后端骨架，具备 `Gateway + Auth + Device + Home` 主链路，并已形成 `Rule/Shadow/MQTT Adapter/Data Parser` 的演进服务边界。
- 当前的主要问题不是“没有路线”，而是路线分散在 `AI-native`、`管理后台`、`技术版本`、`架构交付包` 多份文档中，缺少一份能够从 `AIOT 产研负责人` 视角统一串联业务价值、专项建设、技术治理和组织交付的总纲。
- 未来 12 个月的目标不是继续堆功能，而是完成从“可运行后端”到“可运营、可复制、可平台化、可智能化”的升级。

## 2. Constraints（约束）

- 技术栈约束：继续以 `Java 17 + Spring Boot + Spring Cloud Alibaba + MySQL + Redis + EMQX` 为主体，优先复用现有微服务边界。
- 交付约束：现阶段仍以单节点 Compose 与局部服务本地启动作为主验证方式，结论必须区分“当前验证能力”和“目标态平台能力”。
- 组织约束：业务建设、技术治理、发布稳定性需要并行推进，不能让任何一条主线长期脱节。
- 安全约束：所有新增智能能力必须继承现有鉴权、审批、审计和资源归属校验，不允许 AI 或自动化绕过权限体系。

## 3. Boundaries（边界）

- 本路线图包含：`产品经营`、`AI-native`、`平台架构`、`稳定性交付`、`组织治理` 五条主线。
- 本路线图不直接展开：端侧模型部署、复杂财务分账、大规模训练平台、自助 BI、复杂边缘自治 Agent。
- 本路线图默认以现有仓库为主事实来源，并通过专项文档承接细节设计：
  - `AI-native`：[`AIoT_AI_Native_Product_Roadmap`](https://github.com/aidencck/AIOT_Project/blob/main/docs/product/AIoT_AI_Native_Product_Roadmap.md)
  - `管理后台`：[`AIoT_Admin_Backoffice_Roadmap`](https://github.com/aidencck/AIOT_Project/blob/main/docs/product/AIoT_Admin_Backoffice_Roadmap.md)
  - `技术版本`：[`2026Q3-technology-roadmap-v1.1.0.md`](2026Q3-technology-roadmap-v1.1.0.md)

## 4. Endgame（终局）

- 建成一套面向行业场景的 `AIOT 平台产品`，既能承载设备接入和设备运营，也能沉淀数据资产、智能能力、交付方法和组织机制。
- 最终形成三个闭环：
  - `业务闭环`：设备问题可发现、可解释、可处理、可复盘。
  - `策略闭环`：规则可生成、可发布、可验证、可灰度、可回滚。
  - `知识闭环`：经验可沉淀、可检索、可复制、可迁移。

## 5. 当前状态与核心缺口

### 5.1 当前已具备

- 设备主链路：设备接入、鉴权、家庭权限、设备管理、设备影子、配网、基础 OTA 能力。
- 服务底座：统一网关、统一返回、内部接口令牌校验、Redis Stream 可靠消费链路。
- 技术治理：压测基线、发布回滚脚本、基础监控指标、架构交付包框架。
- 路线文档：已有 AI-native、管理后台、技术版本路线图，可作为专项子路线。

### 5.2 当前短板

- 缺少一份总路线图，把产品价值、AI 建设、架构演进、稳定性交付、组织治理整合为一个统一节奏。
- `aiot-rule-engine`、`aiot-shadow-service`、`aiot-mqtt-adapter`、`aiot-data-parser` 仍偏骨架期，产品化程度不足。
- AI 能力仍以规划为主，尚未形成 `事件 -> 检索 -> 诊断 -> 草案 -> 审批 -> 执行 -> 回写` 的完整闭环。
- 管理后台和运营能力已形成路线，但还未与知识反馈、规则治理、经营指标形成统一平台视角。
- 缺少多租户、行业模板、交付配置包、站点复制机制，尚不能证明“可规模化复制交付”。

## 7. 12 个月路线总览

### 7.1 季度总表

| 季度 | 阶段主题 | 核心目标 | 业务结果 | 技术结果 |
| --- | --- | --- | --- | --- |

### 7.2 一句话阶段目标

- `2026Q3`：把平台从“能运行”提升到“能稳定运营”。
- `2026Q4`：把平台从“能运营”提升到“能理解和辅助决策”。
- `2027Q1`：把平台从“能辅助”提升到“能半自动治理并可复制交付”。
- `2027Q2`：把平台从“单项目系统”提升到“平台化行业方案底座”。

## 8. 五条主线

### 8.1 产品经营主线

- `2026Q3`
  - 以管理后台 M0 为核心，完成 `设备接入 -> 告警 -> 工单 -> 结案 -> 复盘` 最小运营闭环。
  - 固化基础看板：在线率、告警趋势、SLA 达成率、一次解决率。
- `2026Q4`
  - 引入知识反馈、客服协同、问题模板化，提升一次解决率和处理一致性。
  - 开始形成面向行业的标准 SOP 和业务模板。
- `2027Q1`
  - 建立项目/租户/行业模板，沉淀可复制交付的初始化配置包。
  - 引入低风险自动分派、规则推荐和巡检建议。
- `2027Q2`
  - 形成平台级经营看板，支持跨项目经营复盘、跨产品线经验复用、行业方案对比。

### 8.2 AI-native 主线

- `2026Q3`
  - 聚焦 `DeviceEvent`、规则执行最小链路、设备数字体和知识底座设计。
- `2026Q4`
  - 落地 `DeviceEvent + Knowledge Base + Copilot + Rule Draft + Approval` 的 M1 能力。
  - 让平台能回答“设备为什么异常、应该怎么处理、是否能生成规则草案”。
- `2027Q1`
  - 引入低风险动作预填、规则灰度、群组和场景级分析。
  - 建立人工反馈回写知识库与规则模板的机制。
- `2027Q2`
  - 建立多角色 Copilot 工作台，支持运营、客服、实施、研发支持的不同上下文。

### 8.3 平台架构主线

- `2026Q3`
  - 补齐 `rule-engine`、`shadow-service`、`mqtt-adapter`、`data-parser` 的产品化边界。
  - 建立统一事件抽象和标准上下文模型。
- `2026Q4`
  - 完成事件中心、知识中心、设备数字体、审批执行中心的第一版。
  - 明确新模块边界：`aiot-ai-service`、`aiot-ops-service`、`aiot-tenant-service` 为目标态候选。
- `2027Q1`
  - 引入租户主数据、站点配置、模板包和开放接口边界。
  - 评估多协议接入优先级，优先规划 `Modbus/OPC UA` 等行业接入。
- `2027Q2`
  - 形成 `设备域 + 运营域 + 智能域 + 交付域` 的平台化结构。

### 8.4 稳定性交付主线

- `2026Q3`
  - 完成 `v1.1.0`：压测口径标准化、环境门禁脚本化、回滚可演练、监控告警可用。
- `2026Q4`
  - 完成 `v1.2.0` 关键能力：链路指标、瓶颈归因、性能治理和事件闭环质量校验。
- `2027Q1`
  - 进入 `v1.2.x ~ v1.3.0` 过渡，强调低风险半自动执行的灰度、容量与回滚。
- `2027Q2`
  - 建立平台版本门禁：功能、稳定性、性能、审计、灰度五类发布证据。

### 8.5 组织治理主线

- `2026Q3`
  - 建立“总路线图 -> 专项路线图 -> 执行蓝图”的文档体系和里程碑评审节奏。
  - 固化每 Sprint 复盘、每月里程碑评审、每版本验收留档。
- `2026Q4`
  - 补齐 ADR、能力矩阵、交付模板、看板口径和 Owner 机制。
- `2027Q1`
  - 将交付包、站点模板、验收清单纳入项目启动与发布流程。
- `2027Q2`
  - 形成跨项目复制方法论和角色手册。

## 10. 执行层里程碑

### 10.1 `2026Q3`：底座收敛与可运营闭环

- 目标：
  - 完成后台 M0、技术 v1.1.0、架构评审机制的统一收口。
- 关键交付：
  - 告警到工单闭环
  - 发布回滚演练与监控告警基线
  - `Rule/Shadow/MQTT/Data Parser` 的边界和验收定义
  - 全项目总路线图和专项文档归位
- 验收锚点：
  - 关键告警可追溯、可建单、可复盘
  - 发布前具备功能、回滚、告警三类证据

### 10.2 `2026Q4`：AI-native M1 与运营复制

- 目标：
  - 完成最小智能闭环并开始把人工经验结构化。
- 关键交付：
  - `DeviceEvent`
  - `DeviceDigitalProfile`
  - 知识切片与检索
  - 诊断 Copilot MVP
  - 规则草案与审批
- 验收锚点：
  - 高频设备问题可给出引用来源的诊断结果
  - 至少三类规则支持草案生成和审批发布

### 10.3 `2027Q1`：半自动治理与多租户交付

- 目标：
  - 让平台开始具备低风险半自动执行和交付复制能力。
- 关键交付：
  - 低风险策略灰度执行
  - 行业模板和站点初始化包
  - 多租户/项目主数据设计
  - 交付脚本、验收清单、站点看板
- 验收锚点：
  - 低风险动作具备审批、灰度、回滚机制
  - 新站点初始化时间和交付一致性可量化改善

### 10.4 `2027Q2`：平台化与行业方案化

- 目标：
  - 让平台具备跨项目经营和跨产品线迁移能力。
- 关键交付：
  - 多角色工作台
  - 行业方案包
  - 规则/知识/执行效果评估
  - 平台开放能力和标准接口
- 验收锚点：
  - 可按行业模板复制方案
  - 可按平台看板进行月度经营复盘

## 13. 风险矩阵

| 风险 | 阶段 | 触发信号 | 缓释策略 |
| --- | --- | --- | --- |
| 路线过散，团队理解不一致 | 全阶段 | 文档和执行节奏脱节 | 以本路线图为总纲，专项文档做子映射 |
| AI 幻觉或越权 | `2026Q4` 起 | 诊断无来源或高风险动作直达执行 | 强制引用来源、审批、上下文绑定和审计 |
| 规则误触发 | `2026Q4 ~ 2027Q1` | 告警误报率高、执行回滚频繁 | 先预览后灰度，逐步开放自动执行 |
| 治理任务被业务挤压 | `2026Q3` 起 | 监控、回滚、验收缺失 | 技术治理写入版本 DoD 与发布闸口 |
| 平台化过早设计 | `2027Q1` 起 | 新模块过多但业务价值不清 | 先站点模板和交付复制，再上多租户平台化 |
