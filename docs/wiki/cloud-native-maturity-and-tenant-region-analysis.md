# 云原生成熟度与多租户/多地域判断（current）

## 目标

把“AIOT-java 是否达到云原生水平”以及“多租户 / 多地域有什么区别”两类问题收敛成一份统一判断文档，避免只停留在概念层讨论。

本文采用三个判断维度：

- 项目体量：代码规模、服务数量、交付资产、复杂度
- 组织能力：当前团队更像研发驱动、轻量 DevOps，还是具备平台/SRE 能力
- 目标场景：当前是否真的需要进入 Kubernetes 平台化、多租户、多地域阶段

## 一句话结论

- AIOT-java 已达到“云原生应用工程化”水平，但尚未达到“云原生平台原生”水平。
- 以当前项目体量和组织能力看，现阶段主运行面采用 `Docker Compose + GitHub Actions + GHCR + 可观测栈` 是合理选择，不应为了概念完整性过早上重平台。
- 当前更合适的定位是：`中型多服务项目，云原生工程能力达标，平台能力未达标`。
- 多租户与多地域不是一回事：
  - 多租户：解决“同一套系统服务多个客户/品牌/组织”的问题
  - 多地域：解决“同一套业务在多个地理区域运行、容灾、合规”的问题

## 项目体量判断

### 代码与服务规模

- 根 POM 已拆分为 `10` 个模块：`aiot-common`、`gateway`、`auth`、`device`、`mqtt-adapter`、`rule-engine`、`shadow`、`data-parser`、`db-migrator`、`home`。
- 排除构建产物与虚拟环境后，仓库内约有：
  - `360` 个 Java 文件
  - `62` 个 `*Test.java` 测试文件
- `docker-compose.yml` 当前编排 `18` 个服务：
  - 业务服务 `8` 个
  - 基础中间件 `4` 个：`MySQL + Redis + Nacos + EMQX`
  - 可观测组件 `6` 个：`Prometheus + Alertmanager + Loki + Promtail + Tempo + Grafana`
- `docs/scripts/compose/monitoring/workflows` 合计约 `143` 个文件，说明仓库已具备较强交付与运行治理痕迹，而不是单纯代码仓库。

### 按体量看当前定位

- 这不是轻量 demo，也不是只有 2~3 个服务的早期原型。
- 这也还不是需要专门平台团队长期维护的大规模平台项目。
- 更准确地说，它落在“中等复杂度、多服务协同、已需要较强工程纪律”的区间。

## 云原生成熟度判断

### 已达到的能力

- 微服务边界已建立：多模块拆分、独立启动单元、网关统一入口、服务发现已接入。
- 容器化已建立：统一 Docker 交付、Compose 编排、镜像仓库 GHCR 已接入。
- 配置外部化已建立：服务配置通过 `Nacos + 环境变量` 管理。
- 健康探针已建立：主要服务已启用 readiness / liveness / Prometheus endpoint。
- 可观测基线已建立：Prometheus、Alertmanager、Loki、Tempo、Grafana 已纳入运行栈。
- 发布治理已建立：CI/CD 已覆盖镜像构建、健康校验、灰度发布、自动回滚。
- 应用侧弹性已建立：Gateway 已具备限流、熔断；部分事件链路具备 ACK、pending 回收、DLQ、补偿。

### 没达到的能力

- 仓库内未形成 Kubernetes / Helm / HPA / GitOps 等平台级资产。
- 运行面仍以 `Compose + SSH + 脚本化发布` 为中心，而不是声明式平台调度。
- 高可用更多体现在应用补偿和探针设计，尚未体现为多副本、跨可用区、平台级弹性和调度自治。
- 基础设施仍以单环境、单编排为主，例如 Compose 内 `Nacos` 为 `standalone` 形态，不等于平台级生产高可用。

### 结论口径

- 如果问题是“这个项目有没有云原生工程实践”：有，而且不弱。
- 如果问题是“这个项目是不是成熟的云原生平台项目”：不是。
- 对当前体量，更准确的表述不是“云原生不够”，而是“云原生工程化足够，平台化还没到必须投入的阶段”。

## 为什么不能只讲概念

判断一个项目是否“到了云原生阶段”，不能只看有没有 Docker、有没有监控、有没有微服务，还要同时看三件事：

- 项目大小：服务数、运行面复杂度、交付频率、故障域数量
- 组织能力：是否有足够平台/SRE 人力长期维护 K8s、告警体系、容量与容灾
- 业务阶段：当前是先求可交付、可放量，还是已经进入大规模多团队协同阶段

对 AIOT-java 来说：

- 如果团队规模仍在 `3~8` 人左右，现在这套形态通常是投入产出比最优。
- 如果进入 `8~15` 人以上、多环境、多业务线并行阶段，平台债会迅速显现。
- 如果进入 `15+` 人、多区域部署、频繁发布、强 SLA 阶段，就应进入 Kubernetes 平台化。

因此，当前问题不是“缺不缺一个 K8s 名字”，而是“什么时候现有组织已经撑不住服务增长和运维复杂度”。

## 多租户与多地域的区别

### 一句话区分

- 多租户：`谁的数据归谁`
- 多地域：`数据和服务放在哪`

### 核心定义

- 多租户：同一套系统同时服务多个客户、品牌、组织、渠道，核心诉求是隔离、复用、配额和商业复制。
- 多地域：同一套业务在多个地理区域独立运行或容灾，核心诉求是时延、合规、可用性和区域化运营。

### 两者不是同一维度

- 多租户是“客户维度隔离”
- 多地域是“地理维度分布”

系统可以是以下任一形态：

- 单租户 + 单地域
- 多租户 + 单地域
- 单租户 + 多地域
- 多租户 + 多地域

## 多租户解决什么问题

### 核心目标

- 一套平台服务多个客户或品牌
- 客户之间数据、配置、权限、配额相互隔离
- 在保证隔离的前提下复用同一套代码和运行底座

### 典型特征

- 数据模型中 `tenant_id` 是一等公民
- JWT / Session / 内部服务调用链路能够透传租户上下文
- 查询默认带租户过滤
- 配置、限流、能力开关、模型配额可按租户定制
- 监控、日志、成本、账单可按租户统计

### 本质

- 多租户首先是产品与数据模型问题，其次才是部署问题。
- 它主要考验研发和产品纪律，而不是先考验基础设施能力。

## 多地域解决什么问题

### 核心目标

- 让不同区域的用户和设备在更近的区域完成接入、处理和存储
- 降低跨洲网络时延
- 满足本地化部署和数据合规
- 在一个地域故障时维持业务连续性或可控降级

### 典型特征

- 请求入口存在按区域路由能力
- MQTT / API / 数据库 / 消息系统按区域部署
- 数据同步与一致性模型按区域设计
- 监控、发布、故障演练、容量规划按区域独立治理
- 架构中通常出现 `region / zone / site` 等部署维度

### 本质

- 多地域首先是基础设施和运维体系问题，其次才是业务路由问题。
- 它主要考验平台/SRE、网络、数据库复制、容灾能力。

## 最容易混淆的概念

### 多租户不等于多用户

- 多用户只是有很多账号。
- 多租户要求这些账号分属于不同组织，且组织间需要强隔离。

### 多地域不等于多环境

- `dev / staging / prod` 是生命周期环境。
- `cn / eu / us` 是地理运行域。
- 环境标签不代表已经完成多地域架构。

### 多地域不等于打了 region 标签

- 监控指标中出现 `region=cn-local` 只是标签治理，不代表区域级架构能力已经落地。
- 真的多地域要求服务、数据、消息、流量入口都具备区域运行和容灾策略。

## 结合 AIOT-java 的现状判断

### 当前更接近什么

- 当前更接近：`单租户 / 单地域 / 单环境主运行面`
- 已具备：环境和观测标签意识，例如监控中存在 `env / cluster / region` 维度
- 尚未具备：
  - 租户模型的一等公民设计
  - 地域化部署、区域流量入口、跨区数据治理

### 现阶段优先级判断

- 如果未来优先目标是“把平台卖给多个客户、品牌、项目交付复用”，应优先做多租户。
- 如果未来优先目标是“全球部署、跨国合规、降低设备接入时延”，应优先做多地域。
- 对大多数此阶段 AIOT 项目，更常见路径是：
  - 先多租户
  - 后多地域

原因很简单：

- 多租户通常更早决定商业闭环
- 多地域通常更晚才成为硬约束，因为它需要更重的平台投入和更强组织能力

## 对当前项目的管理判断

### 当前还能撑多久

如果维持现有业务形态，且没有快速进入多区域、多客户并行交付阶段，则当前架构还能支撑一段时间，前提是继续守住：

- 发布门禁
- 可观测性补强
- 核心链路补偿和回滚演练
- 服务边界不要继续无序膨胀

### 何时必须升级

当以下条件同时出现时，就不应再停留在当前形态：

- 业务服务数增长到 `12~15+`
- 环境数显著增加，或出现多客户、多项目并行交付
- 发布频率、故障恢复要求、SLA 已超过兼职 DevOps 能承载的范围
- 海外/跨区部署成为刚需

### 升级优先顺序

建议的升级顺序不是“先上最重的平台”，而是：

1. 收口租户模型与边界
2. 固化环境与部署参数体系
3. 统一观测、发布、回滚门禁
4. 再评估是否上 Kubernetes / Helm / GitOps
5. 在业务明确需要时再进入多地域设计

## 建议口径

- 当前仍处于 Compose 工程化阶段，尚未进入 Kubernetes 平台化阶段。

### 对内决策

- 不要因为概念焦虑过早重构为大平台架构。
- 优先判断未来 12 个月到底是“多客户复制”先发生，还是“多区域部署”先发生。
- 先解决边界、隔离、门禁问题，再解决平台抽象问题。
