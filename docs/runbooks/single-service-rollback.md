# 单服务回滚 Runbook

## 1. 目的与适用范围
- **目的**：在单个微服务版本发布后出现故障时，快速、安全、可审计地回滚到上一稳定版本，控制用户影响范围并缩短恢复时间。
- **适用范围**：`aiot-*` 任一单服务（如 `aiot-device-service`、`aiot-home-service`、`aiot-rule-engine`）。
- **不适用范围**：跨服务强耦合变更、数据库不可逆变更、基础设施级故障（需升级为多服务/平台级应急预案）。

## 2. 触发条件
满足任一条件即可触发回滚：
- **可用性告警**：5xx 错误率连续 5 分钟超过 2%，或服务可用性低于 99.5%。
- **性能退化**：P95 延迟较基线上升 > 50% 且持续 10 分钟以上。
- **业务异常**：核心链路（登录、设备控制、规则执行、数据上报）失败率异常升高并经值班确认。
- **发布门禁失败**：金丝雀/全量后健康检查未通过，且重试与快速修复无效。
- **安全风险**：发现高危漏洞暴露、鉴权绕过、敏感数据泄露风险。

## 3. 前置检查
执行前必须确认：
- 当前故障定位到**单服务版本**，且目标回滚版本明确（`LAST_KNOWN_GOOD_VERSION`）。
- 回滚窗口已通知相关方（值班、产品、客服/运营）。
- 已冻结该服务进一步变更（暂停自动发布/合并）。
- 已确认数据库迁移为可兼容或可回退（若不可回退需走应急评审）。

## 4. 执行步骤
> 建议使用脚本：`/Users/aiden/Projects/AIOT-java/scripts/rollback_single_service.sh`

1. **确认目标**
   - 确认服务名：`SERVICE_NAME`
   - 确认目标版本：`TARGET_VERSION`
   - 确认部署环境：`ENV`（staging/prod）
2. **冻结流量变更**
   - 暂停该服务自动发布。
   - 记录当前在线版本与实例数。
3. **执行回滚**
   - 触发回滚工作流（GitHub Actions `rollback.yml`）或手工执行：
     ```bash
     /Users/aiden/Projects/AIOT-java/scripts/rollback_single_service.sh \
       --service SERVICE_NAME \
       --to-tag TARGET_VERSION
     ```
4. **观察发布状态**
   - 监控 Pod/实例滚动状态，确保无 CrashLoopBackOff。
   - 检查启动日志、配置加载、依赖连通性（DB/Redis/MQ）。
5. **业务验证**
   - 执行最小冒烟：关键 API、鉴权、写读路径。
   - 对比关键指标恢复情况（错误率、延迟、吞吐）。
6. **恢复流量策略**
   - 若验证通过，逐步恢复正常流量策略与发布节奏。
   - 若验证失败，升级为 P1 事件并转入应急预案。

## 5. 验证清单
- [ ] 服务版本已变更为 `TARGET_VERSION` 且实例全部健康。
- [ ] `/actuator/health` 或健康探针状态为 `UP`。
- [ ] 5xx 错误率恢复至基线阈值以内。
- [ ] P95 延迟恢复到发布前 ±20% 区间。
- [ ] 核心业务场景最少 3 条用例通过。
- [ ] 无新增高危告警（安全、资源、依赖超时）。
- [ ] 观察窗口（建议 30 分钟）内指标稳定。

## 7. RACI
| 活动 | R(负责执行) | A(最终负责) | C(咨询) | I(被通知) |
|---|---|---|---|---|
| 回滚决策 | 值班后端工程师 | 值班 TL/EM | SRE、产品 | 客服、运营 |
| 回滚执行 | 值班后端工程师/SRE | 值班 TL/EM | DBA（如涉及） | 业务方 |
| 验证确认 | QA/值班工程师 | 值班 TL/EM | 产品、SRE | 客服、运营 |
| 事故留痕与复盘 | 值班工程师 | TL/EM | 全链路相关人 | 团队全员 |

## 8. 验收标准
- **时效性**：从触发到回滚完成（TTR）不超过 15 分钟（P1 可放宽至 30 分钟）。
- **有效性**：关键业务可用性恢复，核心指标回归告警阈值内。
- **可审计性**：留痕模板字段完整，附监控与日志证据链接。
- **可复用性**：复盘输出至少 1 条可执行改进项并纳入迭代计划。
