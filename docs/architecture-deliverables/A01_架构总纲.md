# A01 架构总纲

## 文档元信息

- 文档状态：`in-progress`
- 架构 Owner：`<待填写>`
- 生效版本：`v1.1.0`
- 最后更新：`2026-05-04`

## Premise（前提）

- 当前主运行面为 `Gateway + Auth + Device + Home`，部署形态以 `Docker Compose` 为主。
- 事件链路核心依赖 `Redis Stream + Consumer Group + ACK + DLQ`。
- 业务目标优先级：稳定交付 > 快速扩展 > 成本优化。

## Constraints（约束）

- 基础设施现状约束：`Nacos + MySQL + Redis + EMQX` 为当前可依赖基座。
- 演进策略约束：以增量改造为主，禁止高风险“一次性大迁移”。
- 合规安全约束：内部接口必须使用 `X-Internal-Token`，关键链路必须可审计。

## Boundaries（边界）

- 架构覆盖边界：后端微服务、网关、设备接入、事件流、发布回滚、可观测性。
- 非覆盖边界：App/小程序前端体验细节、外部商业化 BI 系统。
- 责任边界：认证主权在 `auth/home/gateway` 既有分工内演进，不在本轮重构。

## Endgame（终局）

- 终局能力：可持续演进、可观测可回滚、关键风险可前置阻断。
- 交付终态：每次版本发布均可提供“目标达成证据”（性能、稳定、安全、成本）。
- 组织终态：架构决策、工程门禁、验收复盘形成闭环机制并可复制。

## 关键指标（建议）

- 可用性：核心 API 月可用性 `>= 99.9%`
- 时延：关键链路 `p95 < 300ms`（按接口分层定义）
- 事件可靠性：消费失败转 DLQ 丢失率 `= 0`
- 发布质量：发布失败后 `15min` 内完成回滚恢复

## 本期不做（Non-Goals）

- 不做跨云多活与跨地域容灾。
- 不做全链路从 Redis Stream 到 Kafka 的一次性迁移。
- 不做未验证业务价值的 AI 能力规模化投产。
